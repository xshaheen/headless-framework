# Residual Review Findings: tenant data placement

Source: the code review of branch `shaheen/feat/tenant-data-placement` (issue #877, stacked on #1012), run against the branch diff before the review fixes. Its five confirmed findings were fixed in "fix(tenancy): harden tenant-routed contexts from review", and three of its testing gaps and one residual risk in the commit after it. No tracker tickets were filed: the work was authorized to push a branch and open a PR, not to create GitHub issues. This file is the durable record.

## Residual Review Findings

- **P3 · `src/Headless.EntityFramework/Contexts/Runtime/HeadlessTenantMigrationsAssembly.cs` · No migration test covers a routed context whose `DefaultSchema` is null.** Every migration fixture uses `DefaultSchema "app"`. With a null default schema, no authored `EnsureSchemaOperation` exists to rewrite, so the tenant schema is created only because the per-schema history table's creation emits one. Add a fixture context without a default schema and scaffolded migrations to prove it.
- **P3 · `src/Headless.MultiTenancy/ConfigurationTenantDataPlacementOptions.cs` · Placement schema names and connection strings are trusted host configuration.** They reach `HasDefaultSchema`, migration operations, and `WithConnectionString` without format validation. That holds while the placement source is operator-controlled. A `UseResolver<T>` that derives schema names from tenant-supplied input relies only on the EF provider's identifier quoting, which was not verified against hostile identifiers.
- **P3 · `tests/*/TenantRoutedContextGuardTests.cs` · The routed-context startup-guard assertion is repeated in seven test projects.** Declined for now: each copy registers a different feature's storage, so a shared helper would save only the three-line validator filter, and the `Headless.Testing` package that ships `TestBase` would need a reference to `Headless.MultiTenancy` it does not have today.

## Settled decisions the implementation departs from

- **The pin happens at context construction, not at first connection open.** The settled guardrail pins at first connection open. EF builds the model, which carries the schema, inside the `HeadlessDbContext` constructor, so the pin moved earlier. That is stricter than the settled wording and loses no protection. The routed context's `TenantId` returns the pinned id, and a singleton interceptor still rechecks the ambient tenant on every connection open and every EF-issued command.
- **The connection string is applied in `OnConfiguring` from the pinned placement; the interceptor only enforces it.** The settled mechanics put the connection string in `ConnectionOpening`. The factory already resolved the placement asynchronously before constructing the context, and applying it before any connection exists means the database-identity check always compares against the tenant's database, never the shared one. A derived `OnConfiguring` that skips base now fails at construction under both schema and database placements.
- **Routed contexts under a tenant must come from `IDbContextFactory<T>.CreateDbContextAsync`.** This is not a settled decision. Resolving a routed context directly from DI while a tenant is ambient throws, because the placement is resolved asynchronously and the constructor cannot await it. It is the main ergonomic cost of the design, flagged for review.
- **Schema placement refuses every entity mapped to an explicit schema other than the tenant schema, shared entities included.** The plan allowed shared entities to keep an explicit schema. With per-schema migration history each tenant's migrations would create that shared table again, so the model convention now refuses it. A database-only placement keeps explicit schemas.
