Tenant data placement: keep it, park it, or drop it

The schema-per-tenant and database-per-tenant feature is built and tested. You will rarely use it. This page says what it costs you when unused, what the options are, and which of the improvement ideas pay off even for a single shared database.

Date
30 September 2026
Source
Pull requests 1019 and 1030 with the follow-up commits 0e4a53f39 and 340b3f154, the code review in this session, and three research reports on Finbuckle, ABP, Marten, Wolverine, Laravel tenancy, Rails apartment, django-tenants, Hibernate, Quarkus, MikroORM, Prisma, Citus, and Nile.

    The short answer

    Recommendation

    Keep the work, but move it out of the core. Merge it as two opt-in packages behind one small generic hook, label it preview, and build none of the roadmap until a project asks for isolation. A project that keeps every tenant in one database never references the packages and never sees the API.

    Decision taken, 30 September 2026

    The feature is dropped from the core for now. Pull requests 1019 and 1030 are closed without merging and their branches stay in the repository for a later revival. The three ideas that pay off for a shared database continue on their own branches. The record lives in docs/solutions/tooling-decisions/tenant-data-placement-not-adopted-2026-09-30.md.

    Your default is the right default. One shared database with a tenant column is what Microsoft, AWS, PlanetScale, and every library surveyed recommend for most products. Nothing in this feature changes that path. The feature is insurance for the day one customer demands their own schema or database for compliance, backups, or noisy-neighbor reasons.

    The insurance is worth keeping because the expensive parts already exist and pass their tests: rewriting migrations per schema, pinning a context to a tenant, and refusing relay stores on a tenant database. Building those later from nothing is the cost you would pay by deleting the branches. The insurance is worth fencing because its real cost is not runtime. It is that 13 packages now carry hooks that every future change in those paths has to respect.

    What the feature does, in plain words

    Today every tenant's rows live in one database and one schema, and a query filter keeps tenants apart. With placement turned on for one DbContext, a tenant can instead get its own schema, its own database, or stay shared. The context asks a resolver where the tenant lives, pins itself to that answer for its whole life, and throws if the ambient tenant changes underneath it.

    What the two pull requests plus the follow-up commits deliver:

    • A resolver you implement or configure. It returns a schema, a connection string, both, or the shared marker for a tenant and a named data store.
    • A context registered as routed builds its EF model for the tenant's schema and rewrites the scaffolded migrations to that schema, so you scaffold once and migrate every tenant.
    • A pinned context refuses to run once the ambient tenant changes, on every connection open and every command.
    • The outbox, the Jobs store, and the catalog, Settings, Features, and Permissions stores refuse a routed context at startup, because their relays read one fixed database.
    • The HTTP, messaging, and Jobs entry points resolve the placement ahead of the work, so a routed context can be injected into a controller, consumer, or handler.
    • A helper migrates every tenant in the catalog, one after another.

    Your options

    Five options, same fields in the same order. The recommended one is tinted, not enlarged.

    A. Merge both pull requests as they are

    The feature lives in the core packages. Routed contexts can be injected anywhere a Headless entry point set the tenant.

    Cost now
    None beyond review
    Cost if never used
    Hooks in 13 packages, the EF version risk, the reading tax on the tenancy guide
    Cost to reverse
    High. Removal touches 13 packages and 12 test projects
    My view
    Acceptable, but it spends core complexity on a feature you expect to rarely use

    B. Merge 1019 only

    Placement without the entry-point preloading. Routed contexts come only from the factory. The three entry points stay untouched.

    Cost now
    Close 1030 or park it
    Cost if never used
    Hooks in 10 packages instead of 13
    Cost to reverse
    Medium
    My view
    Removes the spread into messaging and Jobs, but the worst maintenance cost is in the EF runtime, which stays

    C. Isolate into opt-in packages recommended

    Move the resolver, cache, preloader, pin, interceptor, and migration rewriter into two packages nobody references by default. The core keeps one small generic hook that entry points call.

    Cost now
    One to two days to move code, add the hook, and relabel docs as preview
    Cost if never used
    Near zero. Two packages that do not load
    Cost to reverse
    Low. Delete two packages
    My view
    Keeps the tested work, keeps the core simple, and makes the delete decision cheap later

    D. Park the branches

    Close both pull requests, keep the branches, revisit when a project needs isolation.

    Cost now
    None
    Cost if never used
    None
    Cost to reverse
    Grows every week. The 1019 branch already needed a 21-commit merge from main after a few days
    My view
    Cheapest today, most expensive the day you need it

    E. Delete the work

    Keep the review notes and the research as documents. Rebuild if and when a project needs isolation.

    Cost now
    None
    Cost if never used
    None
    Cost to reverse
    Rebuild about two weeks of work, and re-solve the migration rewriting and the pin design
    My view
    Only right if you are sure no project will ask for isolation in the next two years

    What would change the recommendation

    Toward A

    A current customer or a signed deal asks for its own schema or database in the next twelve months. Then the hooks in the core earn their keep and isolation only adds indirection.

    Toward D or E

    You decide the framework will target small and medium products only, where one shared database is the whole story. Then keep this page and the research as the record, and delete the branches.

    Risk either way

    Database-per-tenant has no transactional outbox and no enlisted Jobs writes in any option, because the relays read one fixed database. That is why schema-per-tenant is the recommended isolation topology and why the docs now say so.

    The improvement ideas, sorted by whether you need placement for them

    Twelve ideas came out of comparing the design with other ecosystems. Three of them pay off for a single shared database as much as for isolated tenants. The rest only matter once a project uses placement, so they belong on a roadmap, not in the next sprint.

    Advice

    Do idea 9 now. It is a day of work and you will use it in every project. Do idea 4 when the next project needs tenant provisioning of any kind, because permissions, settings, and seed data need the same event. Leave everything else on the roadmap until a real tenant asks for isolation.

    What isolating it would take

    If you pick option C, this is the sequence.

    1. Add one generic hook to the core. A tenancy entry point that sets the tenant runs every registered hook around the rest of the work. The preloader becomes one implementation. The telemetry scope in idea 9 becomes another.
    2. Move the placement types into Headless.MultiTenancy.Placement. The resolver, the request, the configuration source, the cache, the invalidator, and the preloader. The core keeps only the marker that a store must stay on a fixed database.
    3. Move the EF routing into Headless.EntityFramework.TenantRouting. The pin, the interceptor, the model cache key, the migration rewriter, and the migrate-all helper. The context runtime keeps one optional service lookup, as it does today.
    4. Label both packages preview in the docs. Move the placement section of the tenancy guide into its own page and link it from the guide in one sentence.
    5. Write the roadmap once. The twelve ideas with their sizes, in a solutions document, so nobody re-researches them.
    6. Set a review date. Twelve months from merge, if no project references the packages, decide again with this page in hand.
